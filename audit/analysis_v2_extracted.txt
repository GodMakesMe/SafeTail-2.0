3. Runtime Pipeline — How a Request Flows
The system is a three-process-in-one-process simulation: a synthetic traffic generator speaks TCP to a
receiver, which hands chunks to a controller, which schedules onto simulated servers. Understanding this loop
makes every function's role obvious.
# Call What happens
1 main.main() Builds Controller, Receiver, SenderBursts. Calls controller.run().
2 controller.run() Starts receiver.run_async() on a daemon thread; sleeps 1 s to let the socket bind.
3 sender.run() Generates 500,000 Request objects via request_factory, batches them into chunks of 5,
and dispatches them in random-sized bursts (2–4 chunks) over TCP with random
inter-burst sleeps.
4 receiver._process_conne Length-prefixed recv fi np.load(allow_pickle) fi stamps arrival_time fi
ction() controller.send_to_server(arr).
5 controller.send_to_serv One chunk = one unit of work. Iterates requests, calls process_step() per request under
er() a lock. After chunks_per_episode (3) chunks, calls finalize_episode().
6 controller.process_step Per request: poll server availability fi estimate delay on all servers fi populate request
() state from CSVs fi pick action (DQN or baseline) fi schedule on chosen servers fi
compute step reward fi log.
7 controller.finalize_epi Computes episodic reward, writes it back over every step experience, stores to replay
sode() memory, triggers agent.experience_replay(), plots every 20 episodes.
Key structural observation
A step in the code is one request, and an episode is 3 chunks × 5 requests = 15 requests. Training therefore
happens once per 15 requests, and every one of those 15 experiences is stored with the same episodic reward
value, overwriting the individual step rewards that were computed. This is a meaningful deviation from standard
DQN credit assignment and is discussed in §9.

6. Function-wise Explanation
6.1 Entry point and traffic generation
main.request_factory(i) is deliberately paranoid: four nested fallbacks (full Request fi minimal Request fi
SimpleNamespace fi None) because it runs inside the sender's hot loop where an exception would kill traffic
generation. Note that it hardcodes message_size=1024 and bandwidth=20 for every request — so
input-size variability, which both ST and HED treat as a first-class driver of transmission latency, does not exist
in the generated workload.
SenderBursts.run() produces burstiness with random.randint(min_burst, max_burst) chunks per
burst and random.uniform(min_interval, max_interval) seconds between bursts. This is
uniform-random burstiness, not a Poisson arrival process (see §8.2).
6.2 Request and server modelling
Request.fill_server_np() is the contract that makes heterogeneity tractable. It concatenates 9 scalars
(ram_usage, gpu_usage, gpu_memory, time_exec, time_process, cpu_core_used, total_ram, total_cpu_cores,
total_gpu_memory) with 6 variable-length arrays (cpu_usage per core, per-script process/exec times, files per
script, cpu_clock, gpu_clock). Because core counts differ across servers, these vectors have different lengths
per server — which is precisely the problem the encoder exists to solve.
Server.compute_request_time() sums three terms: propagation (sampled from the empirical pool),
transmission (sampled from a hardcoded 5-element list), and computation (regressor output). Critically it is a
pure function — it mutates nothing — which is why process_step can safely call it on all 5 servers to build the
state before committing to an action.
Server._choose_first_letter_for_regressor() encodes contention as a string. If a detection request arrives
while a speech and a predict job are already running, the combined string becomes something like "dps", and
the regressor is asked for the row matching that exact co-execution pattern. This is a clever trace-lookup
scheme, but it means contention is modelled only at the granularity of which task types are co-resident — not
how loaded the machine actually is right now.
6.3 The DQN agent
agent.request_to_state_array() flattens the entire Request via vars(). This is elegant but fragile: adding any
attribute to Request silently changes the state vector's length and meaning, and the ordering depends on
attribute insertion order. Dicts are skipped, so server_dicts contributes nothing — only server_np
matters.
DQNAgent.build_model() merges the encoder and the Q-network into one graph so gradients flow
end-to-end. The encoder handles variable length via Input(shape=(None,1)) plus
GlobalAveragePooling1D. The docstring records the anti-overfitting changes made during development:
layer widths halved, sigmoid replaced with ReLU, dropout added at 0.3/0.4, and — importantly — softmax
removed from the output because it is wrong for Q-value regression. That last change is exactly where the
code parts ways with ST's specified architecture (§8.1).
DQNAgent.experience_replay() pads variable-length states with -1.0 to a common length, computes
standard Bellman targets, and clips them to [-10,10] to stop MSE from exploding. The
validation_split=0.2 on a replay minibatch is unusual — it holds out 20% of a randomly sampled batch
purely to produce a val_loss curve for plots; it does not regularise anything meaningfully.

compute_step_reward() returns, per server, log((1-cm)(1-cu)(1-gm)(1-gu) + 1) where the four
terms are RAM, CPU-core, GPU-memory and GPU-core utilisation fractions. The product is near 1 for a fully
idle server and near 0 for a saturated one, so the reward lies in [0, log 2] — it is a pure resource-headroom
signal. Latency does not appear in it at all. The docstring advertises a different formula (1 + log(exp(·) -
1)) than the code implements.
compute_episodic_reward() combines three terms: the g-discounted sum of step rewards, the satisfaction w
= SP(T)/expected_requests_per_episode, and a normalised average-waiting-time penalty. The waiting-time
denominator is a weighted sum of D1 values scaled by per-type completion ratios — but those ratios are
computed from request_x_done counters that are incremented in send_to_server for every request
regardless of whether it met its deadline (the deadline-conditional increments in compute_step_reward are
commented out). The ratio is therefore effectively 1.0 by construction.
finalize_episode() performs the credit assignment that most defines this system's learning behaviour: every
stored experience receives the episodic reward, not its own step reward. Combined with next_state ==
state in the stored tuple, the temporal-difference target degenerates towards r + g·max Q(s) on the same
state — a substantial departure from textbook DQN.

What the codebase actually is
Stripped of the papers' vocabulary, the running system is: a heterogeneity-aware, redundancy-capable DQN
scheduler whose objective function is resource headroom plus deadline satisfaction. It inherits its
structure from HED (central controller, per-device heterogeneous state, learned encoder, two-level reward), its
action space and baselines from ST (subset enumeration, e-greedy, capacity admission,
Rand/MinLoad/MinProp), and its satisfaction function from the BTP report's cleaner reformulation.
The single most consequential gap is that tail latency — the stated objective of all three documents —
never appears in the reward signal. ST encoded it through the target latency t and the asymmetric penalty
for exceeding it; that mechanism was not carried over. What replaced it optimises for idle resources and
deadline hits, which correlates with good tail behaviour but does not target it. Any percentile improvement
observed in results is therefore an emergent side-effect of redundancy, not a directly optimised quantity.
The second most consequential gap is the missing Oracle baseline. Without it, the optimality-gap analysis
that made ST's evaluation persuasive (Table V: SafeTail within 8–30% of optimal while using 1–3 of 5 servers)
cannot be reproduced here.

12. New findings
12.1 The step reward has no redundancy cost, and is monotone increasing in |A| HIGH
compute_step_reward ( controller.py:285 ) allocates rewards = np.zeros(num_servers) and fills only the
indices in action_subset , leaving unselected servers at 0.0 . Each filled entry is log(product + 1.0)
( controller.py:434 ), bounded in [0, log 2] . The controller then collapses it with
np.mean(final_step_reward_list) ( controller.py:676 ) — a mean over all five slots, divided by a constant.
The step reward is therefore (1/5)·Σ log(1 + headroom ) . Every additional server contributes a non-
i∈A i
negative term to a fixed denominator, so adding any server weakly increases the reward, always. No term
anywhere in either reward level is decreasing in |A| . The compute cost of redundancy is unpriced.
The episodic reward does not compensate: its three terms are the discounted step sum (increasing in |A| ), the
satisfaction ω (increasing, since completion is a min over the subset), and a mean-waiting-time penalty that
redundancy also reduces. All three push the same direction.
12.2 The agent learns to over-replicate HIGH
The prediction from §12.1 is borne out. Recomputing the true per-episode selection rate from
request_wise_access_log.csv (15,225 requests, 15 per episode):

12.3 The reported access-rate curve is a cumulative mean MEDIUM
access_rate_log.csv is not a per-episode series. Its value at episode i equals the expanding mean of the first
15(i+1) entries of request_wise_access_log.csv — verified exactly at episodes 0, 10, 100, 500 and 1014, and
its final value (0.7105812807881775) is bit-identical to the overall request-wise mean.
A cumulative average is damped by construction: it cannot exhibit non-monotonic behaviour, and it understates the
endpoint (0.71 reported versus 0.78 actual). The bottom row of BTP Fig 5.1 is therefore the wrong statistic for the claim
§6.2 draws from it, in addition to that claim being wrong on the merits.
12.4 The baseline comparison is confounded by replication budget HIGH
Every baseline is capped at a fixed K ∈ {1,2,3} servers ( controller.py:622–639 , via
_select_minload_servers(x) and siblings). SafeTail is free to select any of the 31 non-empty subsets, and
converges to K ≈ 3.9. It therefore spends more compute per request than any policy it is compared against, for
83% of training.
BTP Figure 5.2 does not isolate the contribution of learned scheduling. Some unknown share of the p95/p99
gap is explained by replication budget alone — and redundancy is, by the report's own §6.1, "the most effective
known countermeasure against tail latency."
This is the finding most likely to be raised at review, and it is cheap to resolve: re-run the baselines at K = 4 and K =
5 , or subsample SafeTail's decisions to a matched mean K , and report the comparison at equal budget. Until that is
done, no claim of the form "SafeTail beats MinLoad/MinProp/Random at the tail" is supportable.

12.7 Replay memory stores the post-outcome state HIGH
§9 finding #3 of the base report notes next_state == state . There is a second, independent defect on the same
path.
controller.py:724–729 appends the live Request object into step_experiences . agent.store — which is
what actually flattens the object into a state vector — is not called until finalize_episode ( controller.py:798 ),
at the end of the episode. By that time the same object has been mutated in place:
request.total_processing_delay has been overwritten with the realised per-server latencies
( controller.py:671 ), replacing the pre-action estimates written at line 584.
request.combination has been overwritten with the contention string, e.g. "dps" ( servers.py:215 ).
request.queue_waiting_time has been set ( controller.py:649 ).
Because request_to_state_array flattens every attribute (§11.1), the state vector written into replay memory
contains the outcome of the action it is paired with, and is not the state the agent observed when it chose that
action. This is distinct from the _build_features leak in §9 finding #2 — that one contaminates the latency
regressors; this one contaminates the RL training signal directly.
12.8 The workload carries no variation MEDIUM
main.request_factory sets message_size = 1024 and bandwidth = 20 as literals for all requests; only the
type letter ( s / p / d ) is drawn at random ( main.py:86–106 ). Transmission delay ignores both fields, sampling
random.choice([18.5, 19.2, 20, 21.5, 22]) / 1000 ( servers.py:93–94 ). BTP §3.3's "input and output data
sizes that determine transmission delay" and "computational characteristics (FLOPs, input dimensions)" have no
representation in the code. Every request of a given type is identical.
12.9 The run processes 15,225 requests, not 500,000 MEDIUM
These are two different quantities and the smaller one binds. total_no_request = 500000 sizes the pre-generated
pool in SenderBursts.__init__ , but the dispatch loop terminates after no_of_burst = 1000 bursts
( sender_bursts.py:105 ). At E[burst_size] = 3 chunks × 5 requests, that is ≈15,000 — matching the 15,225 in
the logs exactly. BTP Table 4.2's "500,000 requests / 25,000 episodes" overstates the experiment by roughly 33×. The
shipped logs are not truncated; the configuration simply cannot reach the stated figure.
